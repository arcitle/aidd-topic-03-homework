# Восстановленные функциональные требования — Investing Demo

## Дополнительные возможности инвестора

1. Аутентифицированный пользователь управляет собственными ценовыми уровнями для акций: выше/ниже заданной цены. При входе цены в условие создаётся событие в кабинете; повторное событие возможно после выхода цены из условия и нового входа.
2. Пользователь ведёт виртуальный основной портфель: записывает покупки и продажи с количеством и ценой, просматривает операции и позиции с количеством, средней ценой приобретения, текущей стоимостью и нереализованным результатом. Продажа сверх имеющегося количества запрещена.
3. При каждом успешном обновлении котировки цена записывается в БД с временной меткой. Кабинет показывает накопленные точки, фильтрует их по акции и периоду, строит график и считает абсолютное/процентное изменение между первой и последней точками периода.
4. Пользователь создаёт ценовые стратегии покупки/продажи для своего портфеля. При входе котировки в заданное условие формируется виртуальная сделка и запись попадает в общую историю операций. Стратегия срабатывает повторно после выхода цены из условия. Автопродажа ограничена доступной позицией.
5. Доступ к кабинету и всем записям ограничен владельцем; новые сущности удаляются каскадно при удалении владельца, портфеля или акции.

Функциональность доступна по адресу `/investor/` после входа. События оповещений являются внутренними уведомлениями в кабинете; внешняя доставка email/push не настроена.

Документ описывает **фактически реализованное** поведение системы по исходному коду.  
Желаемые или предполагаемые возможности, а также дефекты реализации, **не** включены в перечень требований (дефекты и неоднозначности вынесены в отдельный раздел).

## 1. Основные функциональные возможности

1. Просмотр постраничного списка акций с тикером, названием, ISIN, текущей ценой и цветовой индикацией тренда.
2. Просмотр детальной информации об акции и исторического графика цены.
3. Добавление, редактирование и удаление акций через веб-интерфейс (для аутентифицированных пользователей).
4. Регистрация, вход и выход пользователя.
5. REST API для CRUD-операций над акциями с фильтрацией, поиском, сортировкой и пагинацией.
6. Управление акциями через Django Admin.
7. Первичная загрузка каталога акций из Tinkoff Invest API (management-команда).
8. Периодическое фоновое обновление последней цены и признака роста/падения цены (Celery).

## 2. Основные сценарии взаимодействия

### Сценарий S1. Гость просматривает список акций

1. Пользователь открывает главную страницу `/`.
2. Система отображает таблицу акций (или сообщение «Акций еще нет») с пагинацией.
3. Кнопки «Добавить» / «Редактировать» / «Удалить» не показываются.

### Сценарий S2. Гость открывает карточку акции

1. Пользователь переходит по ссылке с тикера на `/<id>`.
2. Система показывает название, текущую цену, валюту, время обновления и график за последние 180 дней (данные Tinkoff).

### Сценарий S3. Регистрация и вход

1. Пользователь открывает `/user/login/` или `/user/registration/`.
2. При регистрации вводит email и пароль дважды; при успехе система создаёт пользователя, выполняет вход и перенаправляет на главную.
3. При входе вводит email и пароль; при успехе выполняется вход и redirect на главную; при ошибке показывается сообщение о неверных данных.
4. С главной аутентифицированный пользователь может выйти через `/user/logout/`.

### Сценарий S4. CRUD акций через веб (аутентифицированный пользователь)

1. Пользователь нажимает «Добавить», заполняет форму всех полей `Share` и сохраняет → redirect на список.
2. Пользователь нажимает «Редактировать», изменяет поля и сохраняет → redirect на список.
3. Пользователь нажимает «Удалить», подтверждает удаление → запись удаляется, redirect на список.
4. Неаутентифицированный доступ к create/update/delete приводит к redirect на главную.

### Сценарий S5. Работа через REST API

1. Клиент обращается к `/api/v1/shares/` и `/api/v1/shares/<id>/`.
2. Выполняет list / retrieve / create / update / partial_update / destroy.
3. При list может использовать фильтры `name`, `ticker`, поиск по `name`, сортировку и limit/offset-пагинацию.

### Сценарий S6. Администрирование и первичное наполнение

1. Администратор работает с моделью `Share` в `/admin/`.
2. Оператор выполняет `python manage.py add_shares` для загрузки инструментов из Tinkoff в БД.

### Сценарий S7. Фоновое обновление цен

1. Celery Beat инициирует задачу `update_last_price`.
2. Для каждой акции система запрашивает последнюю цену в Tinkoff, обновляет `last_price` и `is_trend_high` в БД.

## 3. Бизнес-правила, проверки и ограничения

| ID | Правило | Где реализовано |
|----|---------|-----------------|
| BR-1 | `figi`, `ticker`, `uid` уникальны | `Share` model constraints |
| BR-2 | Поля `last_price`, `is_trend_high`, `updated_at` допускают пустые значения | модель `Share` |
| BR-3 | Веб-создание/изменение/удаление акций доступно только аутентифицированным пользователям | `IsUserAuthenticatedMixin` |
| BR-4 | Просмотр списка и детали акции доступны без аутентификации | `ShareListView`, `ShareDetailView`, шаблоны |
| BR-5 | При регистрации пароли должны совпадать | `RegistrationForm.clean` |
| BR-6 | Email при регистрации не должен быть уже занят | `RegistrationForm.clean` |
| BR-7 | Email и пароль обязательны при регистрации и входе | поля форм `required=True` |
| BR-8 | Список акций на веб-странице сортируется по `name`, по 100 записей на страницу | `ShareListView` |
| BR-9 | API-список пагинируется LimitOffset с `PAGE_SIZE=100` | `REST_FRAMEWORK` в settings |
| BR-10 | API поддерживает фильтры по `name`/`ticker`, ordering по `name`/`ticker`, search по `name` | `ShareViewSet` |
| BR-11 | При обновлении цены: если новая цена ≥ старой (или сравнение невозможно) — `is_trend_high=True`, иначе `False` | `update_last_price` |
| BR-12 | Цена на графике — дневные свечи за 180 дней по FIGI | `get_graph` |
| BR-13 | Первичная загрузка не дублирует существующие записи (`get_or_create`) | `add_shares` |
| BR-14 | В API-ответе акции отсутствуют поля, не перечисленные в serializer (в т.ч. `uid` не отдаётся) | `ShareSerializer` |
| BR-15 | Цвет ячейки цены: зелёный при `is_trend_high`, иначе красный | `list.html` |

## 4. Функциональные требования

Каждое требование описывает наблюдаемое поведение системы и подтверждается исходным кодом.

### 4.1. Просмотр акций (веб)

1. **FR-1.** Система должна отображать на главной странице (`/`) список акций из БД с полями тикер, название, ISIN, текущая цена и валюта.  
   *Подтверждение:* `dashboard/views.py` (`ShareListView`), `dashboard/templates/dashboard/list.html`.

2. **FR-2.** Список акций на главной странице должен быть отсортирован по полю `name` и разбит на страницы по 100 записей.  
   *Подтверждение:* `ShareListView.paginate_by = 100`, `ordering = ["name"]`; пагинация в `list.html`.

3. **FR-3.** Если в БД нет акций, система должна показывать сообщение «Акций еще нет».  
   *Подтверждение:* ветка `{% else %}` в `list.html`.

4. **FR-4.** Тикер в списке должен быть ссылкой на страницу детали акции `/<id>`.  
   *Подтверждение:* `{% url 'dashboard:detail' share.id %}` в `list.html`.

5. **FR-5.** Ячейка текущей цены должна подсвечиваться зелёным цветом, если `is_trend_high` истинно, и красным — в противном случае.  
   *Подтверждение:* условная разметка в `list.html`.

6. **FR-6.** На странице детали акции система должна показывать наименование, текущую цену с валютой и время последнего обновления (`updated_at`).  
   *Подтверждение:* `ShareDetailView`, `detail.html`.

7. **FR-7.** На странице детали акции система должна отображать интерактивный линейный график цены, построенный по дневным свечам Tinkoff Invest API за последние 180 дней для FIGI данной акции.  
   *Подтверждение:* `dashboard/services/graph.py` (`get_graph`), встраивание `plot_div` в `detail.html`.

### 4.2. Управление акциями (веб)

8. **FR-8.** Аутентифицированный пользователь должен иметь возможность создать акцию через форму на `/create`, содержащую все поля модели `Share`, с последующим сохранением в БД и перенаправлением на главную.  
   *Подтверждение:* `ShareCreateView`, `ShareModelForm` (`fields = "__all__"`), `create.html`.

9. **FR-9.** Аутентифицированный пользователь должен иметь возможность изменить существующую акцию через `/update/<id>` с теми же полями формы и redirect на главную после сохранения.  
   *Подтверждение:* `ShareUpdateView`.

10. **FR-10.** Аутентифицированный пользователь должен иметь возможность удалить акцию через `/delete/<id>` после подтверждения на странице удаления, с redirect на главную.  
    *Подтверждение:* `ShareDeleteView`, `delete.html`.

11. **FR-11.** Кнопки «Добавить», «Редактировать» и «Удалить» должны отображаться в UI только для аутентифицированных пользователей.  
    *Подтверждение:* `{% if user.is_authenticated %}` в `list.html`.

12. **FR-12.** При попытке неаутентифицированного пользователя открыть create/update/delete система должна перенаправить его на главную страницу.  
    *Подтверждение:* `IsUserAuthenticatedMixin.test_func` / `handle_no_permission` → `redirect("dashboard:index")`.

13. **FR-13.** При сохранении акции через веб-форму система должна применять ограничения модели: обязательность строковых полей и уникальность `figi`, `ticker`, `uid`.  
    *Подтверждение:* `dashboard/models.py`, `ShareModelForm`.

### 4.3. Аутентификация и регистрация

14. **FR-14.** Система должна предоставлять страницу входа `/user/login/` с полями email и пароль.  
    *Подтверждение:* `AuthView`, `AuthForm`, `user/templates/user/auth.html`.

15. **FR-15.** При успешной аутентификации система должна создавать пользовательскую сессию и перенаправлять на главную страницу.  
    *Подтверждение:* `login(request, user)` и `redirect("dashboard:index")` в `AuthView.post`.

16. **FR-16.** При неуспешной аутентификации система должна повторно показать форму входа с сообщением «Неверный логин или пароль! Повторите попытку.»  
    *Подтверждение:* ветка `else` в `AuthView.post`.

17. **FR-17.** Система должна предоставлять регистрацию по `/user/registration/` с полями email, пароль и подтверждение пароля.  
    *Подтверждение:* `RegistrationView`, `RegistrationForm`, `registration.html`.

18. **FR-18.** При регистрации система должна отклонять запрос, если пароли не совпадают, с сообщением «Введенные пароли не совпадают».  
    *Подтверждение:* `RegistrationForm.clean`.

19. **FR-19.** При регистрации система должна отклонять запрос, если email уже зарегистрирован, с соответствующим сообщением об ошибке.  
    *Подтверждение:* проверка `User.objects.filter(email=email)` в `RegistrationForm.clean`.

20. **FR-20.** При успешной регистрации система должна создать пользователя (username и email = введённый email), выполнить вход и перенаправить на главную.  
    *Подтверждение:* `RegistrationForm.save` (`create_user`), `login` в `RegistrationView.post`.

21. **FR-21.** Система должна завершать сессию пользователя по запросу `/user/logout/` и перенаправлять на главную.  
    *Подтверждение:* `LogoutView`.

22. **FR-22.** В шапке главной страницы для гостя должна отображаться кнопка «Войти», для аутентифицированного пользователя — приветствие с email и кнопка «Выход».  
    *Подтверждение:* `dashboard/templates/dashboard/base.html`.

23. **FR-23.** Со страницы входа должна быть доступна навигация на регистрацию и наоборот.  
    *Подтверждение:* ссылки в `auth.html` и `registration.html`.

### 4.4. REST API

24. **FR-24.** Система должна предоставлять REST-ресурс `/api/v1/shares/` для получения списка акций.  
    *Подтверждение:* `ShareViewSet`, `router.register(r"shares", ...)`, тесты `test_share_list`.

25. **FR-25.** Система должна предоставлять получение одной акции по `/api/v1/shares/<id>/` и отвечать 404, если запись не найдена.  
    *Подтверждение:* `ModelViewSet.retrieve`, тесты `test_share_detail`, `test_share_detail_invalid`.

26. **FR-26.** Система должна позволять создавать акцию методом POST `/api/v1/shares/` и возвращать статус 201 при успехе; при неполных обязательных данных — 400.  
    *Подтверждение:* тесты `test_share_create`, `test_share_create_invalid`; `ShareSerializer`.

27. **FR-27.** Система должна позволять обновлять акцию методом PUT `/api/v1/shares/<id>/` (полный набор обязательных полей serializer); при неполных данных — 400.  
    *Подтверждение:* тесты `test_share_update`, `test_share_update_invalid`.

28. **FR-28.** Система должна позволять удалять акцию методом DELETE `/api/v1/shares/<id>/` со статусом 204; для несуществующего id — 404.  
    *Подтверждение:* тесты `test_share_delete`, `test_share_delete_invalid`.

29. **FR-29.** В ответах API акция должна сериализоваться с полями: `id`, `figi`, `isin`, `name`, `ticker`, `currency`, `last_price`, `is_trend_high`, `updated_at`.  
    *Подтверждение:* `ShareSerializer.Meta.fields`.

30. **FR-30.** Список API должен поддерживать фильтрацию по `name` и `ticker`, поиск по `name` и сортировку по `name`/`ticker`.  
    *Подтверждение:* `ShareFilter`, `ShareViewSet.filter_backends`, `ordering_fields`, `search_fields`.

31. **FR-31.** Список API должен поддерживать пагинацию LimitOffset с размером страницы по умолчанию 100.  
    *Подтверждение:* `REST_FRAMEWORK` в `config/settings.py`; структура `results` в тестах.

### 4.5. Администрирование и интеграция с рынком

32. **FR-32.** Модель `Share` должна быть доступна в Django Admin со списком полей `figi`, `isin`, `name`, `ticker`, `currency` и поиском по `figi`, `isin`, `name`, `ticker`.  
    *Подтверждение:* `dashboard/admin.py` (`ShareAdmin`).

33. **FR-33.** Management-команда `add_shares` должна загружать инструменты из Tinkoff Invest API (`instruments.shares`) и создавать записи `Share` с полями `figi`, `name`, `isin`, `ticker`, `currency`, `uid` без дублирования существующих (через `get_or_create`).  
    *Подтверждение:* `dashboard/management/commands/add_shares.py`.

34. **FR-34.** Фоновая задача `update_last_price` должна для каждой акции в БД запрашивать последнюю цену по FIGI в Tinkoff API и сохранять значение в `last_price`.  
    *Подтверждение:* `dashboard/tasks.py`, `dashboard/services/market_data.py`.

35. **FR-35.** При обновлении цены система должна выставлять `is_trend_high=False`, если новая цена строго меньше предыдущей `last_price`, и `is_trend_high=True` в остальных обрабатываемых случаях (включая отсутствие корректного предыдущего значения).  
    *Подтверждение:* логика сравнения в `update_last_price`.

36. **FR-36.** Задача обновления цен должна запускаться по расписанию Celery Beat, заданному в конфигурации приложения.  
    *Подтверждение:* `config/celery.py` (`beat_schedule` → `dashboard.tasks.update_last_price`).

## 5. Неоднозначности, противоречия и возможные дефекты реализации

Ниже перечислены проблемы кода и расхождения; они **не являются** функциональными требованиями.

### 5.1. Неоднозначности и противоречия

1. **Интервал обновления цен.** Имя задачи в Beat — `add-every-5-min`, фактически `schedule: 10.0` (секунды). Неясно, какой интервал задумывался.
2. **Доступ к REST API.** Веб-CRUD требует аутентификации, API CRUD открыт без permission-классов. Противоречие моделей доступа между веб и API не задокументировано в коде.
3. **Поле `uid`.** Обязательно и уникально в модели / веб-форме, но отсутствует в `ShareSerializer`; create через API в тестах передаёт `uid`, однако serializer его не объявляет — фактическое поведение create с `uid` зависит от того, игнорируются ли лишние поля DRF.
4. **Смысл `is_trend_high`.** При равенстве цен выставляется `True` («растёт»), что спорно с точки зрения семантики «рост».
5. **Точность цены.** Из Tinkoff берётся только `price.units` (целая часть), дробная часть (`nano`) игнорируется — фактическая цена может отличаться от рыночной.
6. **Регистрация vs шапка.** В `base.html` нет прямой ссылки на регистрацию (только «Войти»); регистрация доступна со страницы входа — путь неочевиден.
7. **`UserPassesTestMixin` вместо `LoginRequiredMixin`.** При отказе всегда redirect на index без сообщения; поведение «отказа в доступе» выглядит как обычный переход на главную.

### 5.2. Возможные дефекты реализации

1. **`AuthView.post` не вызывает `form.is_valid()`** — берёт данные из `form.data`, минуя валидацию формы.
2. **Вход использует `email` как `username`**, а проверка уникальности при регистрации идёт по `email`; при рассинхроне username/email вход может ломаться (сейчас оба пишутся одинаково в `save`).
3. **Ошибка регистрации:** обращение к `form.errors["__all__"].data[0].message` хрупкое и может падать, если структура ошибок иная.
4. **`ShareDetailView`:** `Share.objects.get(id=pk)` без обработки `DoesNotExist` → необработанный 500 вместо 404.
5. **`get_or_create` в `add_shares`** передаёт все поля как lookup-параметры: при частичном совпадении FIGI с другими отличающимися полями возможны исключения уникальности или неожиданное поведение.
6. **Ошибки Tinkoff в `update_last_price` / `get_graph`** логируются или пробрасываются; для UI детали сбой API приводит к падению страницы.
7. **Сравнение тренда** при `last_price is None` даёт исключение, перехватываемое широко (`except Exception`), после чего тренд принудительно `True`.
8. **Пустые `SECRET_KEY` и `TINKOFF_TOKEN`** в settings — приложение и интеграции не готовы к запуску «из коробки».
9. **URL пользователя** смонтирован как `path("user", ...)` без завершающего `/` у префикса — рабочие пути вида `/user/login/`, но префикс неканоничен.
10. **Тест `test_share_create`** передаёт `ticker: "TESTTEST"` (8 символов) при `max_length=10` — ок, но отражает ручное создание записей в обход биржевых ограничений длины/формата тикера.
11. **Форма create** объявляет `enctype="multipart/form-data"` без файловых полей — лишнее, на поведение не влияет.
12. **Права API:** отсутствие аутентификации на мутациях позволяет любому клиенту менять справочник — вероятно дефект относительно веб-модели доступа, но зафиксировано как реализованное поведение в FR-26–FR-28.

### 5.3. Что сознательно не включено в требования

- Персональные портфели, watchlist, уведомления, история цен в БД, симулятор стратегий — в коде отсутствуют.
- Авторизация/токены для API (JWT, SessionAuthentication в явном виде для защиты ViewSet) — не реализованы как ограничение доступа.
- Отображение `is_trend_high` текстом или иконкой отдельно от цвета ячейки — только цветовая подсветка.
- Гарантированная доставка обновлений цен при недоступности Tinkoff — ошибки только логируются, запись может остаться без обновления.
